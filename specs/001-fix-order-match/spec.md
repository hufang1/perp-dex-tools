# 功能规格说明: 修复Extended成交但Lighter未成交的对冲失败问题

**功能分支**: `001-fix-order-match`
**创建日期**: 2026-01-09
**状态**: 草稿
**用户输入**: Extended交易所订单成交后，bot收到WebSocket通知，但在pending_orders缓存中找不到该订单，导致无法触发Lighter对冲订单，最终造成单边持仓风险

---

## 问题分析

### 根本原因

根据日志分析，问题发生在以下竞态条件场景：

1. **21:32:36.464** - Extended SDK返回成功，order_id=`2009619315649257472`
2. **21:32:36.672** - WebSocket收到ORDER消息，订单状态为FILLED（成交）
3. **21:32:36.721** - bot开始查询pending_orders缓存，显示"Order not found attempt 1"
4. **持续37秒** - bot重试50次查询订单，始终在pending_orders中找不到
5. **21:33:14.213** - 查询超时，错误日志"Could not get order info, assuming order is successful"

### 关键问题点

- **时序问题**: WebSocket回调（`_order_update_handler`）在订单ID被添加到`pending_orders`**之前**就被触发
- **假设错误**: 代码假设WebSocket回调会在订单提交之后才到达，但实际上Extended交易所可能在SDK返回前就已发送WebSocket通知
- **缓存失效**: 当`current_order_id`为None时，bot无法在pending_orders中找到订单，导致对冲逻辑不被触发
- **状态不匹配**: 日志显示`current_order_id=None`，说明订单ID可能还未设置到状态中

## 用户场景 & 测试

### 用户故事 1 - 防止竞态条件导致对冲失败 (优先级: P1)

作为交易机器人操作者，我需要系统能够正确处理Extended交易所订单成交通知的时序问题，确保即使WebSocket消息在订单ID设置之前到达，也能正确触发Lighter对冲订单，避免单边持仓风险。

**为什么这个优先级**: 这是核心风险问题，直接导致资金暴露在单边持仓中，可能造成重大损失

**独立测试**: 可以通过模拟WebSocket消息在订单ID设置前到达的场景进行测试，验证对冲订单是否正确执行

**验收场景**:

1. **假设** 系统提交Extended订单，**当** WebSocket成交消息在订单ID设置前到达，**则** 系统应该缓存该消息并在订单ID设置后立即触发对冲
2. **假设** Extended订单成交但pending_orders中找不到，**当** WebSocket消息包含完整的订单信息，**则** 系统应该直接使用WebSocket消息中的数据触发对冲
3. **假设** 订单查询超时（50次重试失败），**当** 系统已收到WebSocket成交通知，**则** 系统应该基于WebSocket通知继续执行对冲逻辑

作为系统维护者，我需要完整的订单生命周期追踪日志，以便在出现问题时能够快速定位是Extended成交问题、Lighter对冲问题还是中间逻辑问题。

**独立测试**: 可以通过检查日志输出验证所有关键状态转换都被记录

**验收场景**:

1. **假设** 订单提交到Extended，**当** SDK返回成功，**则** 日志应记录order_id和timestamp
2. **假设** WebSocket收到成交消息，**当** 订单在pending_orders中未找到，**则** 日志应记录"使用WebSocket缓存消息处理"
3. **假设** 对冲订单提交到Lighter，**当** 提交成功或失败，**则** 日志应记录完整的对冲订单信息

作为风险管理者，我需要系统能够检测到Extended成交但Lighter未成交的异常情况，并触发紧急熔断机制，防止进一步交易。

**为什么这个优先级**: 这是最后的安全网，虽然P1和P2应该能防止大多数情况，但仍需要兜底保护

**独立测试**: 可以通过模拟Lighter订单失败场景验证熔断是否正确触发

**验收场景**:

2. **假设** 检测到未对冲仓位，**当** 异常情况发生，**则** 系统应停止新的套利机会处理

## 需求

### 功能需求

- **FR-001**: 系统必须能够在WebSocket回调到达时处理`current_order_id`为None的情况，通过缓存机制延迟处理
- **FR-002**: 系统必须在`_order_update_handler`中检查`current_order_id`，如果为None则将订单更新消息缓存到待处理队列
- **FR-003**: 系统必须在设置`current_order_id`后立即检查待处理队列，如果有匹配的订单更新则触发处理
- **FR-004**: 系统必须提供明确的日志区分"通过pending_orders找到订单"和"通过WebSocket缓存处理订单"两种路径
- **FR-005**: 系统必须在订单查询超时时，检查是否收到过WebSocket成交通知，如果有则基于通知继续执行
- **FR-006**: 系统必须记录所有订单状态转换的详细日志，包括时间戳、订单ID、状态变化
- **FR-007**: 系统必须在检测到Extended成交但Lighter未成交时，记录警告到`logs/trade.log`并触发熔断
- **FR-008**: 系统必须支持人工确认后从熔断状态恢复

### 关键实体

- **订单更新缓存 (Order Update Cache)**: 临时存储WebSocket回调中到达但在`pending_orders`中找不到的订单更新消息
  - 属性: `order_id`, `status`, `side`, `size`, `price`, `contract_id`, `timestamp`
  - 用途: 解决WebSocket消息和订单ID设置之间的竞态条件

- **待处理队列 (Pending Queue)**: 按时间顺序排列的订单更新消息队列
  - 属性: `updates[]`, `max_size`, `ttl`
  - 用途: 确保订单更新按正确顺序处理

- **熔断状态 (Circuit Breaker State)**: 系统交易状态标志
  - 属性: `is_tripped`, `reason`, `trip_time`, `uncleared_positions`
  - 用途: 防止在存在未对冲仓位时继续交易

## 成功标准

### 可衡量结果

- **SC-001**: 在100次测试中，WebSocket消息在订单ID设置前到达时，对冲订单成功触发率达到100%
- **SC-002**: 系统能够在50ms内处理缓存的订单更新消息并触发对冲
- **SC-003**: 日志能够清晰区分每笔交易的完整路径（Extended下单 → WebSocket通知 → Lighter对冲 → 成功/失败）
- **SC-004**: 检测到未对冲仓位后，系统在100ms内停止处理新的套利机会
- **SC-005**: 未对冲仓位警告日志包含完整的上下文信息（时间、订单ID、数量、价格、两个交易所的状态）
- **SC-006**: 系统在正常交易运行24小时后，未出现因竞态条件导致的单边持仓

### 性能指标

- 订单更新缓存查询响应时间 < 1ms
- 待处理队列处理延迟 < 50ms
- 熔断触发延迟 < 100ms
- 日志写入延迟不影响交易执行（< 10ms）

## 假设 & 依赖

### 假设

- Extended交易所的WebSocket消息包含完整的订单信息（order_id, status, size, price等）
- WebSocket消息虽然可能乱序，但不会丢失（最终会到达）
- Lighter交易所的订单API在下单后可以同步返回结果
- 系统内存足够维持待处理队列（预计最多缓存100条订单更新）

### 依赖

- Extended WebSocket连接保持稳定
- Lighter订单API在下单时可用
- 文件系统可正常写入日志
- 时钟同步正常（用于判断消息超时）

### 外部因素

- Extended交易所API的稳定性
- 网络延迟的波动范围
- Lighter交易所的订单簿深度
