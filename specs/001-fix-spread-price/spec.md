# Feature Specification: 修复spread套利脚本价格同步问题

**Feature Branch**: `001-fix-spread-price`
**Created**: 2026-01-16
**Status**: Draft
**Input**: User description: "修复spread套利脚本中ext开仓成本高于lig的问题 - 问题在于两个交易所获取价格不是同一时刻，导致价差不一致"

---

## 问题分析摘要

### 当前实现的问题

**问题现象**：
- 在多次开仓后，出现相同仓位（如0.21 ETH）但ext开仓成本高于lig的情况
- 这种情况在套利策略中不应该出现（ext应该低买，lig应该高卖）
- Extended频繁出现"Order not found"和"Taker order not filled, retrying..."日志

**根本原因**（已更新）：

**问题1：价格获取时间不同步**
1. 虽然两个交易所的订单是并发发送的，但每个交易所在下taker订单前都独立获取BBO价格
2. 在ext获取价格和lig获取价格之间的微小时间差内，市场价格可能发生变化
3. 两个交易所使用的是不同时刻的价格作为订单基准

**问题2：Extended缺乏滑点保护导致频繁重试** ⭐ **核心发现**
1. Extended当前实现：买入用`best_ask`，卖出用`best_bid`（0%滑点保护）
2. Lighter当前实现：买入用`best_ask * 1.002`，卖出用`best_bid * 0.998`（0.2%滑点保护）
3. Extended没有滑点保护 → IOC订单经常因流动性不足被取消 → 触发重试
4. **重试时获取新价格** → 导致最终成交价与最初价格不一致 → ext成本高于lig

**代码证据**：
```python
# trade_executor.py:580-587 (Extended)
if side == "buy":
    price = best_ask  # ❌ 没有滑点保护！
else:
    price = best_bid  # ❌ 没有滑点保护！

# trade_executor.py:639-644 (Lighter)
if side == "buy":
    price = best_ask * Decimal('1.002')  # ✅ 有0.2%滑点保护
else:
    price = best_bid * Decimal('0.998')  # ✅ 有0.2%滑点保护
```

**问题3：IOC订单重试导致价格变化**
- Extended交易所客户端内部有重试机制（最多10次）
- 每次重试都会重新获取BBO价格并下单
- 重试期间价格可能发生变化，导致最终成交价不一致

## User Scenarios & Testing

### User Story 1 - 同步价格获取并确保滑点保护 (Priority: P1)

作为套利系统运营者，我希望系统在开仓时能够确保两个交易所使用的是同一时刻的价格，并且都有合理的滑点保护，以避免出现ext开仓成本高于lig的不合理情况。

**为什么这个优先级**：这是核心问题，直接影响到套利策略的盈利能力和风险控制。当前Extended缺乏滑点保护导致频繁重试，重试时价格变化导致最终成交价不一致。

**独立测试**：可以通过以下方式独立测试：
1. 模拟开仓场景，记录两个交易所获取价格的时间戳
2. 验证两个价格获取的时间差是否在可接受范围内（如<10ms）
3. 检查开仓时ext和lig是否都使用了带滑点保护的价格
4. 检查开仓后ext的买入价是否确实低于lig的卖出价

**验收场景**：

1. **给定** 系统处于空闲状态，**当** 检测到套利机会（价差>阈值），**则** 系统应同时获取两个交易所的价格（时间差<10ms）
2. **给定** 获取到两个交易所的价格，**当** 计算taker订单价格，**则** ext买入价 = ask * 1.002，lig卖出价 = bid * 0.998（都加0.2%滑点保护）
3. **给定** 执行开仓操作，**则** ext买入价应 < lig卖出价（考虑到合理的价差）
4. **给定** 开仓成功，**当** 检查持仓成本，**则** ext开仓成本应低于lig开仓成本（符合套利逻辑）
5. **给定** 价格获取时间差>10ms，**当** 检测到这种情况，**则** 系统应记录警告并可选择跳过此次开仓机会
6. **给定** IOC订单因流动性不足被取消，**当** 检测到重试，**则** 重试应使用原始价格（不重新获取）或放弃重试

---

### User Story 2 - 价格获取优化减少延迟 (Priority: P2)

作为套利系统运营者，我希望系统在获取价格时能够最小化延迟，以提高套利的成功率和准确性。

**为什么这个优先级**：优化价格获取延迟可以提高系统整体性能，但不是解决当前问题的核心方案。

**独立测试**：
1. 测量从SpreadMonitor获取价差到实际下单的总耗时
2. 优化后对比优化前的延迟数据

**验收场景**：

1. **给定** 需要获取两个交易所的价格，**当** 系统并发获取价格，**则** 总耗时应接近较慢的那个交易所（而非两者之和）
2. **给定** 价格获取完成，**当** 下发订单，**则** 从价格获取到订单发送的时间应<50ms

---

### User Story 3 - 添加价格一致性监控 (Priority: P3)

作为套利系统运营者，我希望系统能够监控并记录每次开仓时的价格获取时间差，以便于问题诊断和系统优化。

**为什么这个优先级**：这是监控和诊断功能，不影响核心套利逻辑，但有助于长期维护。

**独立测试**：
1. 检查日志中是否记录了每次开仓的价格获取时间戳
2. 验证监控指标是否正确计算和展示

**验收场景**：

1. **给定** 系统执行开仓操作，**当** 获取两个交易所的价格，**则** 系统应记录每个价格获取的时间戳
2. **给定** 开仓完成，**当** 查看开仓日志，**则** 应能看到价格获取时间差和实际成交价信息

### Edge Cases

- **价格剧烈波动**：当市场价格在短时间内剧烈波动时，可能导致即使时间差很小，价格仍不一致
  - 处理方案：设置最大可接受价格偏差阈值，超过则跳过此次开仓

- **交易所API延迟**：当某个交易所API响应变慢时，可能导致价格获取时间差增大
  - 处理方案：设置API超时时间，超时则放弃此次开仓

- **订单成交价格与预期不符**：由于使用taker订单，实际成交价可能与获取的BBO价格有滑点
  - 处理方案：使用IOC订单并设置合理的滑点缓冲（0.2%）

- **网络分区或连接问题**：某个交易所连接断开时
  - 处理方案：检测连接状态，异常时不进行开仓

- **IOC订单流动性不足**：当对手盘流动性不足时，IOC订单会被取消并触发重试
  - 处理方案：加入0.2%滑点保护降低失败率；重试时使用原始价格而非重新获取BBO

- **重试期间价格大幅变化**：当Extended内部重试期间，市场价格可能发生较大变化
  - 处理方案：禁用内部重试或限制重试次数为1次；重试使用原始价格

- **滑点保护后的价差倒挂**：加入滑点保护后，可能出现ext买入价 >= lig卖出价的情况
  - 处理方案：检测这种情况，跳过此次开仓并记录警告

## Requirements

### Functional Requirements

**价格同步与滑点保护**：
- **FR-001**: 系统必须在开仓前同时获取两个交易所的BBO价格（时间差<10ms）
- **FR-002**: 系统必须确保ext的买入价格低于lig的卖出价格（价差为正）
- **FR-003**: 系统必须在计算taker订单价格时加入滑点保护：
  - Extended买入价格 = ask * 1.002（加0.2%滑点）
  - Extended卖出价格 = bid * 0.998（减0.2%滑点）
  - Lighter保持现有逻辑（已有0.2%滑点保护）

**重试控制**：
- **FR-004**: 系统必须禁用或限制Extended交易所客户端的内部自动重试机制
- **FR-005**: 系统必须在IOC订单被取消时，使用原始价格重试（不重新获取BBO价格），或直接放弃重试
- **FR-006**: 系统必须限制重试次数为最多1次，避免多次重试导致价格大幅变化

**监控与日志**：
- **FR-007**: 系统必须在价格获取时间差超过阈值时记录警告日志
- **FR-008**: 系统必须在检测到价格不一致（ext买入价 >= lig卖出价）时跳过此次开仓
- **FR-009**: 系统必须记录每次开仓的价格获取时间戳、滑点调整后价格和实际成交价
- **FR-010**: 系统应使用并发方式获取价格以最小化总延迟
- **FR-011**: 系统应在价格获取失败或超时时放弃开仓并记录错误

**代码清理与验证**：
- **FR-012**: 系统必须确保spread套利脚本只使用taker模式方法（`_place_*_order_taker`）
- **FR-013**: 系统必须确保所有taker订单都传入 `time_in_force=0` (IOC) 参数
- **FR-014**: 系统必须给Maker模式方法（`place_open_order`, `get_order_price`）添加弃用标记或文档说明
- **FR-015**: 系统必须验证spread目录中没有调用Maker模式方法的代码

### Key Entities

- **价格快照（PriceSnapshot）**：
  - ext_bid: ext交易所的买一价
  - ext_ask: ext交易所的卖一价
  - lig_bid: lig交易所的买一价
  - lig_ask: lig交易所的卖一价
  - ext_timestamp: ext价格获取时间戳
  - lig_timestamp: lig价格获取时间戳
  - time_delta: 两个时间戳之差

- **开仓记录（OpenPositionRecord）**：
  - price_snapshot: 开仓时使用的价格快照
  - ext_order_id: ext交易所订单ID
  - lig_order_id: lig交易所订单ID
  - ext_execution_price: ext实际成交价
  - lig_execution_price: lig实际成交价
  - status: 开仓状态（成功/失败/部分成交）

## Success Criteria

### Measurable Outcomes

**价格同步与一致性**：
- **SC-001**: 100%的开仓操作中，两个交易所价格获取时间差<10ms
- **SC-002**: 100%的开仓操作中，ext和lig都使用了0.2%滑点保护
- **SC-003**: 0%的开仓操作出现ext买入价 >= lig卖出价的情况（价格一致性）
- **SC-004**: 开仓后ext开仓成本<lig开仓成本的比例达到100%（符合套利逻辑）

**重试控制**：
- **SC-005**: Extended IOC订单失败率从当前水平降低至少80%（通过加入滑点保护）
- **SC-006**: 100%的重试操作使用原始价格而非重新获取BBO价格
- **SC-007**: 单次开仓的最大重试次数不超过1次

**整体性能**：
- **SC-008**: 因价格不一致而放弃开仓的频率<5%（避免过度敏感）
- **SC-009**: 价格获取到订单发送的平均延迟<50ms（性能指标）
- **SC-010**: 所有一次开仓失败（单边成交）的情况都有详细的日志记录

---

## Assumptions

1. 交易所API能够在10ms内返回BBO价格
2. 网络延迟相对稳定（<50ms）
3. 两个交易所的WebSocket连接都是活跃的
4. 当前已使用taker订单（IOC模式）确保即时成交
5. 开仓方向固定：ext做多，lig做空
6. 0.2%的滑点保护足以让大部分IOC订单成功成交（基于Lighter的经验）
7. Extended交易所客户端的内部重试机制可以被禁用或绕过
8. 使用原始价格重试不会显著增加成交失败率

## Out of Scope

以下内容不在本feature范围内：
- 修改套利策略的基本逻辑（ext做多、lig做空）
- 改变taker订单模式为maker订单模式
- 优化订单簿WebSocket连接（已有独立机制）
- 修改平仓逻辑（平仓使用相同的价格同步机制）
- 添加新的交易所支持
- 动态调整滑点大小（当前固定为0.2%，未来可考虑根据市场波动率动态调整）
- 实现真正的市价单（Market Order）接口，因为Extended SDK不支持
- 修改Extended SDK源码，只能通过封装实现

## 代码清理要求

### 发现的Maker模式代码（需处理）

**问题代码位置**：
1. `trade_executor.py:512-553` - `_place_lighter_order()` 和 `_place_extended_order()` 方法（未使用的非taker实现）
2. `exchanges/lighter.py:326-403` - `place_open_order()` 和 `get_order_price()` 方法（Maker模式实现）

**处理方案**：
- **选项1（推荐）**：给这些方法添加 `@deprecated` 装饰器并添加弃用警告文档
- **选项2**：删除或重命名这些方法（加上 `_legacy_` 前缀）
- **选项3**：保持现状，但在代码注释中明确说明这些是Maker模式，不应在spread套利中使用

**验证要求**：
- 确保 `spread/` 目录中的所有代码都使用taker模式方法（`_place_*_order_taker`）
- 确保 `time_in_force=0` (IOC) 参数被正确传递
- 不应调用 `place_open_order` 或 `get_order_price` 方法
