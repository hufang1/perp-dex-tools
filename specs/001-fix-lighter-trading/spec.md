# 功能规格说明：修复Lighter交易所下单失败和日志混乱问题

**功能分支**: `001-fix-lighter-trading`
**创建日期**: 2026-01-12
**状态**: 草稿
**用户输入**: 修复套利程序中Lighter下单总是失败和日志标识混乱的问题

## 用户场景与测试 *(必填)*

### 用户故事 1 - 统一日志标识清晰区分交易所 (优先级: P1)

用户在查看套利程序日志时，需要能够清晰地区分哪条日志来自Extended交易所，哪条来自Lighter交易所，以便快速定位问题和调试。

**为什么这个优先级**: 日志混乱严重影响问题诊断效率，当出现单腿持仓或其他问题时，无法快速定位是哪个交易所出现问题。

**独立测试**: 可以通过运行程序并检查日志输出来验证。所有Extended交易所的日志应包含`[EXTENDED]`标签，所有Lighter交易所的日志应包含`[LIGHTER]`标签。

**验收场景**:

1. **给定** 套利程序正在运行, **当** Extended交易所下单时, **那么** 日志必须包含`[EXTENDED]`标识
2. **给定** 套利程序正在运行, **当** Lighter交易所下单时, **那么** 日志必须包含`[LIGHTER]`标识
3. **给定** 日志文件打开, **当** 查看任何交易相关日志, **那么** 应该能够通过标识立即判断来自哪个交易所
4. **给定** 发生错误, **当** 查看错误日志, **那么** 错误日志必须明确标识是Extended还是Lighter的错误

---

### 用户故事 2 - 修复Lighter交易所下单失败问题 (优先级: P0 - 阻塞问题)

用户需要套利程序能够在两个交易所同时成功下单，避免出现单腿持仓的情况。当前Lighter下单总是失败，导致只有Extended成交，需要紧急平仓，增加了风险和手续费成本。

**为什么这个优先级**: 这是阻塞性问题，导致套利策略无法正常运行，每次都会触发紧急平仓，无法实现盈利。

**独立测试**: 可以通过触发一次套利机会来验证。两个交易所应该同时并发下单，并且都成功返回订单ID。

**验收场景**:

1. **给定** 发现套利机会, **当** 发起双腿并发下单, **那么** Extended和Lighter都应该成功返回订单ID
2. **给定** 并发下单开始, **当** Lighter下单, **那么** 不应该抛出`AttributeError: 'NoneType' object has no attribute 'code'`错误
3. **给定** 两个交易所都成功下单, **当** 查看日志, **那么** 应该看到"双腿成交"而不是"单腿持仓"
4. **给定** 使用代理连接, **当** 初始化Lighter客户端, **那么** 代理设置应该正确应用到REST客户端

---

### 用户故事 3 - 紧急平仓统一使用Taker订单 (优先级: P1 - 优化)

当出现单腿持仓需要紧急平仓时，系统应该使用taker订单而不是maker订单，确保能够立即成交退出头寸，避免进一步损失。

**为什么这个优先级**: 紧急平仓时速度至关重要，使用maker订单可能会被拒绝或延迟成交，增加风险暴露时间。

**独立测试**: 可以通过模拟单腿持仓场景来验证。紧急平仓订单应该使用taker模式（post_only=False）立即成交。

**验收场景**:

1. **给定** 检测到单腿持仓, **当** 执行紧急平仓, **那么** 订单应该使用taker模式（post_only=False）
2. **给定** 紧急平仓订单发送, **当** 订单到达交易所, **那么** 应该立即成交或被拒绝（不应该挂单等待）
3. **给定** 紧急平仓完成, **当** 查看日志, **那么** 应该明确显示使用的是taker订单类型

---

### 边界情况

- **代理连接失败**: 当配置的代理服务器无法访问时，系统应该如何处理？是否应该回退到直连？
- **Lighter SDK初始化失败**: 当`lighter_client.check_client()`返回错误时，是否应该重试？
- **并发下单超时**: 当一个交易所下单超时（超过500ms），另一个交易所已经成交，应该如何处理？
- **订单ID为None**: 当SDK返回的订单ID为None时，是否应该认为下单失败？
- **WebSocket回调延迟**: 当订单已提交但WebSocket回调在5秒内未到达，是否应该查询API验证？
- **网络波动**: 在并发下单过程中出现网络波动，导致一个订单发送失败，系统应该如何处理？
- **部分成交**: 当一个订单完全成交，另一个订单部分成交，应该如何处理？
- **订单查询失败**: 当查询Lighter订单状态失败时，应该如何处理？

## 需求 *(必填)*

### 功能需求

- **FR-001**: 系统必须在所有Extended交易所相关日志中包含`[EXTENDED]`标识标签
- **FR-002**: 系统必须在所有Lighter交易所相关日志中包含`[LIGHTER]`标识标签
- **FR-003**: 系统必须在错误日志中明确标识错误来自哪个交易所（Extended或Lighter）
- **FR-004**: 系统必须修复Lighter SDK初始化问题，确保`api_client.rest_client.proxy`正确设置
- **FR-005**: 系统必须验证Lighter客户端初始化后`check_client()`返回None（表示成功）
- **FR-006**: 系统必须在并发下单时确保两个交易所同时发起请求（间隔<5ms）
- **FR-007**: 系统必须捕获并记录Lighter SDK的`AttributeError`异常的完整堆栈信息
- **FR-008**: 系统必须在紧急平仓时使用taker订单（post_only=False）确保立即成交
- **FR-009**: 系统必须在下单失败时不影响另一个交易所的正常下单流程
- **FR-010**: 系统必须记录每个订单的发送时间戳和响应时间戳
- **FR-011**: 系统必须在下单失败时提供明确的错误消息（包括SDK异常类型和消息）

### 关键实体

- **日志记录器**: 记录交易所操作的日志，必须包含交易所标识（EXTENDED/LIGHTER）、时间戳、操作类型、订单ID、状态
- **订单结果**: 包含订单ID、成交状态、成交数量、成交价格、错误信息（如果失败）
- **并发执行结果**: 包含Extended和Lighter两个交易所的订单结果、发送时间差、总执行时间、是否单腿持仓

## 成功标准 *(必填)*

### 可衡量的结果

- **SC-001**: 程序运行时，100%的Extended相关日志包含`[EXTENDED]`标识
- **SC-002**: 程序运行时，100%的Lighter相关日志包含`[LIGHTER]`标识
- **SC-003**: Lighter下单成功率从当前的0%提升到90%以上（10次尝试中至少9次成功）
- **SC-004**: 并发下单时，两个交易所的发送时间差保持在5ms以内
- **SC-005**: 紧急平仓订单100%使用taker订单模式（post_only=False）
- **SC-006**: 单腿持仓发生率从当前的100%降低到10%以下
- **SC-007**: 用户能够在30秒内通过日志识别出问题交易所（Extended或Lighter）
- **SC-008**: 错误日志包含完整的异常堆栈和SDK错误消息
