# 功能规格说明：价差套利系统改进

**功能分支**: `003-spreading-improvements`
**创建日期**: 2026-01-19
**状态**: 草稿
**输入**: 用户描述：修复重复挂单bug，实现阶梯价差开仓，双模式平仓逻辑（限价/市价），以及可用仓位检测系统

## 用户场景与测试

### 用户故事 1 - 修复重复挂单Bug (优先级：P1)

系统在修改挂单价格时，必须确保先取消旧订单，再创建新订单，避免出现多个挂单同时存在的情况。

**为什么是此优先级**：这是一个严重bug，会导致资金占用超出预期、风险管理失效，可能造成重大损失。

**独立测试**：可以通过模拟修改挂单价格的场景，验证系统能否正确取消旧订单后再创建新订单。

**验收场景**：

1. **已知** 系统持有一个有效的挂单，**当** 价差变化需要修改挂单价格，**则** 系统先取消旧订单，等待取消确认后再创建新订单
2. **已知** 旧订单取消失败（网络错误或交易所拒绝），**则** 系统停止创建新订单，记录错误并进入安全状态
3. **已知** 系统尝试修改挂单价格，**当** 检查交易所挂单列表，**则** 只能存在一个活跃的挂单

---

### 用户故事 2 - 阶梯价差开仓 (优先级：P1)

系统采用阶梯式价差阈值进行开仓，首次开仓使用初始价差阈值，后续每次开仓的阈值递增一个固定步长。

**为什么是此优先级**：这是核心交易策略的改进，直接影响套利系统的盈利能力和资金使用效率。

**独立测试**：可以通过模拟价差波动场景，验证系统能否按照阶梯阈值正确触发开仓。

**验收场景**：

1. **已知** 初始开仓价差设置为 0.5%，步长为 0.1%，**当** 首次检测到价差达到 0.5%，**则** 系统执行第一次开仓
2. **已知** 已执行一次开仓，**当** 价差达到 0.6%（初始值 + 1 × 步长），**则** 系统执行第二次开仓
3. **已知** 已执行两次开仓，**当** 价差达到 0.7%（初始值 + 2 × 步长），**则** 系统执行第三次开仓
4. **已知** 已执行一次开仓，**当** 价差在 0.55%（小于第二次阈值 0.6%），**则** 系统不执行开仓，继续监控

---

### 用户故事 3 - 双模式平仓逻辑 (优先级：P2)

系统根据利润水平选择限价平仓或市价平仓：利润较小时使用限价单降低成本，利润较大时使用市价单快速兑现。

**总开仓仓位的平均价差计算方式**：系统从交易所 API 获取两个交易所的总持仓信息，分别计算出 Extended 和 Lighter 的平均开仓成本（成交量加权平均价），然后计算两者的价差作为总开仓仓位的平均价差。如果交易所 API 不提供平均开仓成本，则使用本地记录的每次开仓价格进行加权平均计算。

**为什么是此优先级**：这优化了平仓策略，在保证风险控制的同时最大化利润。

**独立测试**：可以通过模拟不同的价差场景，验证系统能否根据利润大小选择正确的平仓方式。

**验收场景**：

1. **已知** Extended 总持仓的平均开仓成本为 100,000 USDT，Lighter 总持仓的平均开仓成本为 100,800 USDT，总开仓仓位的平均价差为 0.8%，限价平仓阈值 A = 0.2%，市价平仓阈值 B = 0.4%，**当** 当前价差为 0.5%（处于 0.4% 到 0.6% 之间），**则** 系统使用限价单平仓
2. **已知** 总开仓仓位的平均价差为 0.8%，**当** 当前价差为 0.3%（小于 0.8% - 0.4% = 0.4%），**则** 系统使用市价单立即平仓
3. **已知** 系统使用限价平仓，**则** 状态转换为 PLACING_CLOSING_ORDER，等待订单成交
4. **已知** 系统使用市价平仓，**则** 状态转换为 CLOSING_POSITION_MARKET，立即执行平仓
5. **已知** 交易所 API 返回平均开仓成本失败，**当** 系统尝试计算平仓阈值，**则** 使用本地记录的每次开仓价格进行加权平均计算总开仓仓位的价差

---

### 用户故事 4 - 可用仓位检测系统 (优先级：P3)

系统在开仓前（Extended 挂单和 Lighter 对冲之前）检查两个交易所的可用余额是否足够支持目标仓位，如果任一交易所余额不足则跳过本次开仓机会。这确保了在执行任何交易操作之前，两个交易所都有足够的资金支持，避免出现 Extended 仓位充足但 Lighter 仓位不足导致单边持仓的风险。

**为什么是此优先级**：这是风控增强功能，防止因余额不足导致的交易失败或单边持仓风险。

**独立测试**：可以通过模拟不同的余额状态，验证系统能否正确判断并拒绝余额不足的开仓请求。

**验收场景**：

1. **已知** Extended 交易所可用 USDT 余额为 1000，目标开仓需要 1200，**当** 系统检测到套利机会，**则** 在发送任何订单之前跳过本次开仓，记录余额不足日志
2. **已知** Lighter 交易所可用代币余额为 500，目标开仓需要 1000（Extended 余额充足），**当** 系统检测到套利机会，**则** 在 Extended 挂单之前就跳过本次开仓，避免单边持仓风险
3. **已知** 两个交易所余额都充足，**当** 系统检测到套利机会，**则** 先通过余额检测，然后正常执行 Extended 挂单和 Lighter 对冲逻辑
4. **已知** 系统跳过开仓，**则** 状态保持不变（IDLE 保持 IDLE，HOLDING 保持 HOLDING），继续监控价差，不发送任何订单到任一交易所

---

### 边界情况

- 当修改挂单价格时，取消订单超时（交易所无响应）会发生什么？
  继续取消，知道取消成功
- 当获取交易所平均开仓成本失败时，如何计算平仓阈值？
  可以用开仓价差平均值代替
- 当阶梯开仓次数过多（如超过 10 次）时，是否需要设置最大开仓次数限制？
  不需要
- 当市价平仓时遇到流动性不足（无法完全成交）如何处理？
  暂时不用考虑
- 当可用余额刚好等于目标开仓所需金额时，是否需要保留缓冲余量？
  不用，直接开仓
- 当价差在两个阈值之间快速波动时，如何避免频繁切换平仓模式？
  暂时没有想到好方法

## 需求

### 功能需求

#### 重复挂单修复

- **FR-001**: 系统 MUST 在修改挂单价格时，先执行取消订单操作，等待取消成功后再创建新订单
- **FR-002**: 系统 MUST 在取消订单后验证旧订单确实已从交易所活跃订单列表中移除
- **FR-003**: 系统 MUST 在取消订单失败时停止创建新订单，记录错误并进入安全状态
- **FR-004**: 系统 MUST 确保在任何时间点，每个交易所最多只有一个活跃的套利挂单

#### 阶梯价差开仓

- **FR-005**: 系统 MUST 支持配置初始开仓价差阈值（如 0.5%）
- **FR-006**: 系统 MUST 支持配置开仓步长（如 0.1%）
- **FR-007**: 系统 MUST 在第 N 次（N >= 1）开仓时使用阈值：初始价差 + (N-1) × 步长
- **FR-008**: 系统 MUST 在所有开仓价差检测的输出和逻辑中使用阶梯阈值计算
- **FR-009**: 系统 MUST 记录当前开仓次数，用于计算下一次开仓的阈值
- **FR-010**: 系统 MUST 在平仓成功后重置开仓次数为 0

#### 双模式平仓逻辑

- **FR-011**: 系统 MUST 从交易所 API 获取两个交易所的总持仓信息，分别计算 Extended 和 Lighter 的平均开仓成本（成交量加权平均价）
- **FR-012**: 系统 MUST 计算总开仓仓位的价差：`(Lighter 平均开仓成本 - Extended 平均开仓成本) / Extended 平均开仓成本`
- **FR-013**: 系统 MUST 支持配置两个平仓阈值变量：限价平仓阈值 A 和市价平仓阈值 B（其中 B > A）
- **FR-014**: 系统 MUST 在满足 `当前价差 < 总开仓价差 - B` 时使用市价单立即平仓
- **FR-015**: 系统 MUST 在满足 `总开仓价差 - B < 当前价差 < 总开仓价差 - A` 时使用限价单平仓
- **FR-016**: 系统 MUST 在市价平仓和限价平仓时使用不同的状态转换逻辑
- **FR-017**: 系统 MUST 在无法从交易所 API 获取平均开仓成本时使用降级策略：使用本地记录的每次开仓价格进行加权平均计算

#### 可用仓位检测

- **FR-018**: 系统 MUST 在开仓前（发送任何订单之前）检查 Extended 交易所的可用 USDT 余额是否 >= 目标开仓所需金额
- **FR-019**: 系统 MUST 在开仓前（发送任何订单之前）检查 Lighter 交易所的可用代币余额是否 >= 目标开仓数量
- **FR-020**: 系统 MUST 在任一交易所余额不足时跳过本次开仓，不发送任何订单到任一交易所，保持 IDLE 状态
- **FR-021**: 系统 MUST 在余额检测通过后，先执行 Extended 挂单，再执行 Lighter 对冲
- **FR-022**: 系统 MUST 在余额不足时记录详细的日志信息（所需余额、实际余额、缺少金额、哪个交易所不足）
- **FR-023**: 系统 MUST 支持配置余额缓冲比例（如额外保留 5% 的余量），避免刚好用尽的情况

### 关键实体

- **初始开仓价差 (Initial Opening Spread)**：第一次开仓的价差阈值，用户可配置
- **开仓步长 (Opening Step Size)**：每次递增的开仓价差阈值，用户可配置
- **开仓次数 (Opening Count)**：当前已执行的开仓次数，用于计算下一次阈值
- **当前开仓阈值 (Current Opening Threshold)**：第 N 次开仓使用的价差阈值 = 初始价差 + (N-1) × 步长
- **限价平仓阈值 A (Limit Close Threshold A)**：用于判断是否使用限价平仓的价差值
- **市价平仓阈值 B (Market Close Threshold B)**：用于判断是否使用市价平仓的价差值（B > A）
- **总开仓仓位的价差 (Total Position Spread)**：从交易所 API 获取两个交易所的总持仓信息后，分别计算 Extended 和 Lighter 的平均开仓成本（成交量加权平均价），然后计算价差：`(Lighter 平均开仓成本 - Extended 平均开仓成本) / Extended 平均开仓成本`
- **平均开仓成本 (Average Opening Cost)**：从交易所 API 获取的总持仓的平均成本价，或使用本地记录的每次开仓价格加权平均计算
- **可用余额 (Available Balance)**：Extended 的 USDT 余额和 Lighter 的代币余额
- **余额缓冲 (Balance Buffer)**：额外保留的余量比例，防止刚好用尽

## 成功标准

### 可衡量结果

- **SC-001**: 重复挂单bug完全消除，在任何场景下每个交易所最多只有一个活跃挂单
- **SC-002**: 阶梯开仓逻辑准确率达到 100%，所有价差检测点都使用正确的阈值计算
- **SC-003**: 双模式平仓逻辑准确率达到 100%，根据利润大小正确选择限价或市价平仓
- **SC-004**: 余额检测准确率达到 100%，无因余额不足导致的交易失败
- **SC-005**: 系统在价差变化时的响应时间不超过 200 毫秒
- **SC-006**: 市价平仓的执行时间不超过 500 毫秒
- **SC-007**: 所有状态转换（包括市价平仓和限价平仓）都能正确执行，无状态混乱

### 假设

- 交易所 API 提供获取账户平均开仓成本的接口
- 如果交易所不提供平均开仓成本，可以使用本地记录的开仓价格加权平均计算
- 限价平仓阈值 A 和市价平仓阈值 B 由用户根据市场情况配置
- 初始开仓价差和开仓步长由用户根据策略配置
- 余额检测在每次开仓前执行，不影响现有的平仓逻辑
- 市价平仓时交易所流动性足够，可以完全成交目标仓位
- 取消订单操作在正常网络条件下可以在 2 秒内完成

### 依赖

- 现有的价差套利系统（002-spread-arb）已经稳定运行
- 交易所 API 支持获取账户持仓的平均开仓成本
- 交易所 API 支持查询可用余额
- 系统状态机支持市价平仓和限价平仓的区分
