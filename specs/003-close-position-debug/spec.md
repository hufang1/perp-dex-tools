# Feature Specification: 平仓逻辑修复与持仓监控调试

**Feature Branch**: `003-close-position-debug`
**Created**: 2026-01-09
**Status**: Draft
**Input**: User description: "修复自动平仓逻辑并添加持仓监控调试信息

问题描述：
从运行日志可以看到，套利程序触发强制平仓后一直无法成功平仓，出现重复的强制平仓警告。日志显示：
- 持仓时间超过最大限制（1800秒）仍然持续增长到1900+秒
- PnL显示亏损（-$0.31至-$0.32）
- 成功平仓数始终为0
- 强制平仓操作被重复触发

优化需求：
1. 修复自动平仓逻辑，确保平仓操作能够正确执行
2. 在开仓后到平仓前的等待期间，向控制台打印详细的持仓状态信息
3. 动态获取两个交易所（Lighter和Extended）的实际仓位和收益数据
4. 显示当前持仓时间、距离最大持仓时间还有多久
5. 显示当前盈亏状态和距离盈利目标的差距
6. 所有输出使用简体中文"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 修复平仓执行失败问题 (Priority: P1)

作为套利程序用户，我需要系统能够在触发平仓条件时成功执行平仓操作，而不是无限期地持有亏损仓位。

**Why this priority**: 这是核心功能缺陷，直接导致资金损失和系统风险。当前平仓操作完全失败，造成仓位持续亏损且无法退出。

**Independent Test**: 可以通过模拟触发平仓条件来测试，验证平仓订单是否成功提交并执行。

**Acceptance Scenarios**:

1. **Given** 套利对持仓时间超过最大限制（1800秒），**When** 触发强制平仓逻辑，**Then** 系统应向两个交易所提交平仓订单并成功平仓
2. **Given** 套利对达到盈利目标，**When** 触发盈利平仓逻辑，**Then** 系统应提交平仓订单并成功平仓
3. **Given** 平仓订单提交失败，**When** 检测到失败，**Then** 系统应记录错误日志并采取重试或熔断措施
4. **Given** 平仓订单已提交但未成交，**When** 检查订单状态，**Then** 系统应等待成交或取消后重新提交

---

### User Story 2 - 实时持仓状态监控 (Priority: P2)

作为套利程序用户，我需要在控制台实时查看每个持仓套利对的详细状态，包括持仓时间、实际仓位、当前盈亏等信息。

**Why this priority**: 调试信息对于诊断问题和监控系统运行状态至关重要，但不影响核心交易功能。

**Independent Test**: 可以通过开仓后观察控制台输出来验证，确认所有预期信息都被正确显示。

**Acceptance Scenarios**:

1. **Given** 套利对已开仓但未达到平仓条件，**When** 系统定期检查持仓状态，**Then** 控制台应显示当前持仓时间和距离最大持仓时间的剩余时间
2. **Given** 套利对已开仓，**When** 系统检查状态，**Then** 控制台应显示Extended和Lighter交易所的实际仓位信息
3. **Given** 套利对已开仓，**When** 系统检查状态，**Then** 控制台应显示当前实时盈亏和距离盈利目标的差距
4. **Given** 套利对已开仓，**When** 系统检查状态，**Then** 控制台应使用简体中文显示所有信息

---

### User Story 3 - 动态交易所数据获取 (Priority: P2)

作为套利程序用户，我需要系统能够动态获取交易所的实际仓位和价格数据，而不是仅依赖本地缓存数据。

**Why this priority**: 确保显示的信息与交易所实际状态一致，避免因数据不一致导致的错误决策。

**Independent Test**: 可以通过比对控制台显示的数据与交易所实际数据来验证。

**Acceptance Scenarios**:

1. **Given** 需要显示持仓状态，**When** 系统获取Extended交易所数据，**Then** 应从交易所接口实时获取当前仓位和价格
2. **Given** 需要显示持仓状态，**When** 系统获取Lighter交易所数据，**Then** 应从交易所接口实时获取当前仓位和价格
3. **Given** 交易所接口调用失败，**When** 获取数据失败，**Then** 系统应使用缓存数据并标记为"数据可能过期"

---

### Edge Cases

- 当交易所接口响应缓慢或超时时，如何处理持仓状态显示？
- 当两个交易所的仓位数据不一致时（例如一个成功平仓，另一个失败），系统如何处理？
- 当程序因异常终止重启后，如何恢复并显示正在持仓的套利对状态？
- 当网络中断导致无法获取实时数据时，系统如何继续运行？
- 当持仓时间非常接近最大限制时，显示的剩余时间是否需要特殊格式？

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须在触发平仓条件时成功向交易所提交平仓订单
- **FR-002**: 系统必须在平仓订单提交后持续跟踪订单状态，直到成交或确认失败
- **FR-003**: 系统必须在平仓订单失败时记录详细错误信息并执行适当的恢复策略
- **FR-004**: 系统必须在套利对开仓后定期（至少每5秒）向控制台输出持仓状态信息
- **FR-005**: 系统必须在控制台输出中包含当前持仓时间和距离最大持仓时间的剩余时间
- **FR-006**: 系统必须在控制台输出中包含Extended交易所的实际仓位大小和当前价格
- **FR-007**: 系统必须在控制台输出中包含Lighter交易所的实际仓位大小和当前价格
- **FR-008**: 系统必须在控制台输出中包含当前实时盈亏金额和百分比
- **FR-009**: 系统必须在控制台输出中包含距离盈利目标的盈亏差距
- **FR-010**: 系统必须使用简体中文显示所有控制台输出信息
- **FR-011**: 系统必须在检测到平仓失败时防止重复提交相同的平仓订单
- **FR-012**: 系统必须在交易所接口调用失败时使用缓存数据并标记数据来源

### Key Entities

- **持仓套利对 (Spread Pair Position)**: 表示一个已开仓的套利交易对，包含开仓价格、开仓时间、交易所仓位信息、当前盈亏等状态
- **平仓订单 (Close Order)**: 表示向交易所提交的平仓订单，包含订单ID、提交时间、订单状态（待成交/已成交/已失败）、成交价格等
- **持仓状态快照 (Position Snapshot)**: 表示某一时刻的持仓状态快照，包含两个交易所的实际仓位、当前价格、实时盈亏、剩余持仓时间等信息

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 触发平仓条件后，系统在30秒内成功提交平仓订单的比例达到95%以上
- **SC-002**: 平仓订单提交后，系统在60秒内完成平仓（成交或确认失败）的比例达到90%以上
- **SC-003**: 持仓期间，控制台每5-10秒输出一次完整的持仓状态信息
- **SC-004**: 控制台显示的持仓数据与交易所实际数据的误差小于1%
- **SC-005**: 用户通过控制台输出能够清晰识别当前持仓状态、剩余时间和盈亏情况
- **SC-006**: 系统不再出现无限期持仓且无法平仓的情况
- **SC-007**: 所有控制台输出使用简体中文，信息完整且易于理解

## Assumptions

- Extended和Lighter交易所的API能够提供实时的仓位和价格查询接口
- 交易所API的响应时间在正常情况下小于1秒
- 网络连接稳定，不会频繁中断
- 交易所不会频繁拒绝平仓订单（除非市场异常）
- 系统具有足够的权限执行平仓操作
- 日志记录系统已经正常工作（已在001-trade-log功能中实现）

## Dependencies

- 001-trade-log: 交易日志功能（用于记录平仓操作的详细日志）
- 现有的价差套利机器人主逻辑（spread/bot.py）
- Extended交易所客户端（exchanges/extended.py）
- Lighter交易所客户端（exchanges/lighter_custom_websocket.py）

## Out of Scope

- 修改开仓逻辑或优化开仓策略
- 修改盈利目标或最大持仓时间的设定逻辑
- 添加新的交易所支持
- 实现Web界面或移动端监控界面
- 自动调整仓位大小或风险参数
