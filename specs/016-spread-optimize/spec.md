# Feature Specification: 价差套利程序优化

**Feature Branch**: `016-spread-optimize`
**Created**: 2026-01-13
**Status**: Draft
**Input**: User description: "价差套利程序优化：精简日志、实时价差检测、等差数列开仓、智能平仓、仓位平衡检测、统一taker交易"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 精简日志输出 (Priority: P1)

用户启动套利程序时，程序仅输出关键的启动信息和交易决策信息，避免大量冗余的初始化日志干扰用户视线。关键信息包括：API验证结果、当前价差状态、开仓/平仓决策、仓位平衡检测结果。

**Why this priority**: 日志冗余直接影响用户体验和监控效率，精简日志是基础性改进，能够立即提升程序可用性。

**Independent Test**: 启动程序后，日志输出应当清晰简洁，所有关键信息在一行内完整呈现，可以通过检查日志行数和每行信息密度来验证。

**Acceptance Scenarios**:

1. **Given** 程序启动时，**When** 环境变量验证通过，**Then** 输出单行摘要包含所有关键配置信息（账户索引、API状态、时区等）
2. **Given** 程序运行中，**When** 检测到价差变化，**Then** 输出单行包含Ext bid/ask和Lig bid/ask及计算后的价差
3. **Given** 执行交易操作时，**When** 开仓/平仓，**Then** 输出单行包含操作类型、数量、价格和结果
4. **Given** 程序运行中，**When** 非关键事件发生，**Then** 不输出日志或仅在DEBUG级别输出

---

### User Story 2 - 实时价差监控 (Priority: P1)

程序实时监控两个交易所（Extended和Lighter）的订单簿，计算并显示当前的价差信息，为交易决策提供实时数据支持。

**Why this priority**: 价差监控是套利交易的核心基础功能，没有实时价差数据就无法做出正确的交易决策。

**Independent Test**: 程序运行后能够持续输出两个交易所的bid/ask价格和计算的价差，可以通过验证价格数据的准确性和更新频率来测试。

**Acceptance Scenarios**:

1. **Given** 两个交易所WebSocket连接正常，**When** 订单簿数据更新，**Then** 输出格式如 `价差: Ext[3325.5/3326.5] Lig[3320.0/3321.0] = 5.5 (0.17%)`
2. **Given** 订单簿数据异常，**When** bid<=0或ask<=0或bid>=ask，**Then** 输出错误日志但不中断程序
3. **Given** 价差数据可用，**When** 价差超过最小开仓阈值，**Then** 触发开仓逻辑

---

### User Story 3 - 等差数列开仓策略 (Priority: P1)

当实时价差超过最小开仓阈值时执行开仓，之后每次价差在前次开仓价差基础上增加一个step值时继续开仓，实现价差扩大过程中的分批建仓。

**Why this priority**: 这是核心盈利策略，能够通过等差数列的方式在价差扩大时持续建仓，最大化收益。

**Independent Test**: 设定最小开仓价差0.2%、step0.05%，模拟价差从0.2%逐步上升到0.5%，验证开仓行为符合预期。

**Acceptance Scenarios**:

1. **Given** 当前无仓位，**When** 实时价差>最小开仓阈值(0.2%)，**Then** 执行开仓并缓存当前价差，输出 `开仓: 价差0.25% > 阈值0.2%`
2. **Given** 已有仓位且缓存价差0.25%，**When** 实时价差>0.30%(0.25%+step 0.05%)，**Then** 继续开仓并更新缓存价差为0.30%
3. **Given** 已有仓位且缓存价差0.30%，**When** 实时价差0.28%(未达到0.35%)，**Then** 不开仓，输出 `价差0.28%未达到开仓条件0.35%`
4. **Given** 价差缩小，**When** 实时价差<缓存价差，**Then** 不更新缓存价差，保持原有开仓阈值

---

### User Story 4 - 智能平仓系统 (Priority: P2)

程序实时监控持仓情况，当总仓位的开仓均价价差 >= 当前市场价差 + 盈利目标 + 总手续费时，执行平仓操作锁定利润。

**Why this priority**: 这是盈利实现的关键机制，确保在合适的时机平仓获利，避免价差反转导致亏损。

**Independent Test**: 建立模拟仓位，设定盈利目标0.1%、总手续费0.05%，模拟价差从开仓时的0.3%缩小到0.15%，验证平仓触发。

**Acceptance Scenarios**:

1. **Given** 持有多笔仓位，**When** 总开仓价差 - (当前价差 + 盈利目标 + 手续费) >= 0，**Then** 执行平仓所有仓位
2. **Given** 持仓盈利目标0.1%、手续费0.05%，**When** 开仓时价差0.3%、当前价差0.15%，**Then** 输出 `平仓: 开仓0.3% >= 当前0.15% + 盈利0.1% + 手续费0.05% = 0.3%` 并执行平仓
3. **Given** 持仓中，**When** 未达到平仓条件，**Then** 输出 `持仓: 开仓0.3% vs 当前0.2% (盈利0.1% < 目标0.15%)`
4. **Given** 价差反向扩大，**When** 当前价差 > 开仓价差，**Then** 不平仓，输出警告 `价差扩大: 当前0.35% > 开仓0.3%`

---

### User Story 5 - 仓位平衡检测与保护 (Priority: P2)

开仓后设置可配置的缓冲期（默认3秒），验证两个交易所是否都已成功开仓且仓位数量一致，若不平衡则立即平仓保护资金安全。

**Why this priority**: 仓位不平衡可能导致单边暴露风险，这是重要的风险控制机制。

**Independent Test**: 执行开仓后模拟一侧交易所开仓失败或数量不一致，验证程序在缓冲期内检测到不平衡并执行平仓。

**Acceptance Scenarios**:

1. **Given** 执行双向开仓，**When** 两侧交易所都成功开仓且数量一致，**Then** 输出 `仓位平衡: Ext 0.01 / Lig 0.01`
2. **Given** 执行双向开仓，**When** 缓冲期(3秒)内检测到Ext开仓0.01但Lig开仓0.005，**Then** 立即平仓，输出 `仓位不平衡: Ext 0.01 != Lig 0.005，紧急平仓`
3. **Given** 执行双向开仓，**When** 一侧交易所返回失败，**Then** 立即平仓另一侧，输出 `开仓失败: Ext成功/Lig失败，平仓Ext`
4. **Given** 缓冲期过后，**When** 仓位验证通过，**Then** 正常进入持仓监控状态

---

### User Story 6 - 统一Taker交易模式 (Priority: P3)

所有套利交易（开仓和平仓）统一使用taker模式，确保交易即时执行，避免因挂单未成交导致的错失机会或仓位不平衡。

**Why this priority**: 统一交易模式可以简化逻辑并提高执行的确定性，但优先级略低于核心策略功能。

**Independent Test**: 执行开仓和平仓操作，验证订单以taker方式提交且即时成交。

**Acceptance Scenarios**:

1. **Given** 执行开仓操作，**When** 提交订单到交易所，**Then** 订单以taker模式提交（价格略优于对手价以确保即时成交）
2. **Given** 执行平仓操作，**When** 提交订单到交易所，**Then** 订单以taker模式提交（对手价确保即时成交）
3. **Given** Taker订单提交，**When** 订单成交，**Then** 输出日志明确标注为taker成交

---

### Edge Cases

- 当WebSocket连接断开或订单簿数据停止更新时，程序如何处理？
- 当价差在阈值附近剧烈波动时，等差数列开仓逻辑如何避免频繁开仓？
- 当交易所API返回延迟或超时时，仓位平衡检测如何处理？
- 当程序重启时，如何恢复之前的价差缓存和仓位状态？
- 当手续费或滑点导致实际利润不符合预期时，如何调整策略？
- 当市场出现极端价格（暴涨暴跌）时，程序如何保护资金？

## Requirements *(mandatory)*

### Functional Requirements

#### 日志优化相关
- **FR-001**: 程序启动时必须输出单行配置摘要，包含账户索引、API状态、交易对、数量、开仓阈值、盈利目标等关键信息
- **FR-002**: 程序运行中必须输出单行实时价差信息，格式为 `价差: Ext[bid/ask] Lig[bid/ask] = 价差值 (百分比%)`
- **FR-003**: 交易操作日志必须单行包含操作类型、数量、价格、结果等关键信息
- **FR-004**: 非关键信息（初始化详情、组件状态等）必须从INFO级别移除或降至DEBUG级别

#### 实时价差监控相关
- **FR-005**: 程序必须实时从Extended和Lighter交易所获取订单簿的bid和ask价格
- **FR-006**: 程序必须持续监控并计算两个交易所之间的价差（百分比和绝对值）
- **FR-007**: 当订单簿数据异常（bid<=0或ask<=0或bid>=ask）时必须输出错误日志但继续运行
- **FR-008**: 价差数据更新周期必须与WebSocket订单簿更新频率保持一致

#### 等差数列开仓策略相关
- **FR-009**: 程序必须支持配置最小开仓价差阈值（默认0.2%）
- **FR-010**: 程序必须支持配置价差步进值step（默认0.05%）
- **FR-011**: 当实时价差 > 缓存价差 + step时，程序必须执行新的开仓操作
- **FR-012**: 首次开仓时，当实时价差 > 最小开仓阈值，程序必须执行开仓并缓存当前价差
- **FR-013**: 当价差缩小时，程序必须保持缓存价差不变，不降低开仓阈值

#### 智能平仓系统相关
- **FR-014**: 程序必须支持配置盈利目标百分比（默认0.1%）
- **FR-015**: 程序必须支持配置总手续费率（默认0.05%，包含两个交易所的开仓和平仓手续费）
- **FR-016**: 程序必须实时计算并监控总仓位的开仓均价价差与当前市场价差的差异
- **FR-017**: 当 开仓价差 >= 当前价差 + 盈利目标 + 总手续费 时，程序必须执行平仓所有持仓
- **FR-018**: 平仓时程序必须输出单行日志包含开仓价差、当前价差、盈利目标、手续费、实际利润

#### 仓位平衡检测相关
- **FR-019**: 程序必须支持配置仓位平衡检测缓冲期（默认3秒）
- **FR-020**: 开仓操作后，程序必须在缓冲期内验证两个交易所的仓位是否相等
- **FR-021**: 当检测到仓位不平衡（数量不一致）时，程序必须立即平仓所有持仓
- **FR-022**: 当一侧交易所开仓失败时，程序必须立即平仓另一侧已开的仓位
- **FR-023**: 仓位平衡验证通过后，程序才能进入持仓监控状态

#### 统一Taker交易相关
- **FR-024**: 所有套利交易开仓操作必须使用taker模式（买入时用ask价格，卖出时用bid价格）
- **FR-025**: 所有套利交易平仓操作必须使用taker模式（对手价确保即时成交）
- **FR-026**: taker订单不得使用post_only参数，允许支付taker费用以换取成交确定性

#### 模块解耦相关
- **FR-027**: 实时价差监控功能必须独立实现，可独立测试
- **FR-028**: 等差数列开仓逻辑必须独立实现，可独立测试
- **FR-029**: 智能平仓系统必须独立实现，可独立测试
- **FR-030**: 仓位平衡检测必须独立实现，可独立测试

### Key Entities

- **价差数据**: 包含Extended的bid/ask、Lighter的bid/ask、计算的价差值（绝对值和百分比）、更新时间戳
- **开仓阈值**: 包含最小开仓价差（配置项）、当前缓存的开仓价差、价差步进值step
- **仓位记录**: 包含每个交易所的持仓数量、开仓均价、开仓时间戳
- **平仓计算**: 包含总开仓均价价差、当前市场价差、盈利目标、总手续费、净利润
- **平衡状态**: 包含两个交易所的仓位对比结果、平衡验证状态、缓冲期计时器
- **交易配置**: 包含交易对、交易数量、开仓阈值、盈利目标、手续费率、平衡缓冲期、价差步进值

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 程序启动日志输出不超过10行，且所有关键配置信息在单行内完整呈现
- **SC-002**: 实时价差监控每秒至少更新1次，价差计算准确率达到100%（通过回测验证）
- **SC-003**: 等差数列开仓策略在测试数据集上的开仓时机准确率达到95%以上
- **SC-004**: 智能平仓系统能够在价差回归时及时平仓，平均平仓延迟不超过2秒
- **SC-005**: 仓位不平衡检测能在配置的缓冲期内（默认3秒）100%识别不平衡情况并执行保护性平仓
- **SC-006**: 所有套利交易使用taker模式的成功率达到98%以上（考虑极端市场情况）
- **SC-007**: 各功能模块（价差监控、开仓策略、平仓系统、平衡检测）可独立测试，单元测试覆盖率达到80%以上
- **SC-008**: 程序在7x24小时连续运行中不出现内存泄漏或连接泄漏，稳定性达到99%

## Assumptions & Dependencies

### Assumptions
- Extended和Lighter交易所的WebSocket连接稳定可用
- 两个交易所的手续费率相对固定，可在配置中预设
- 市场流动性足够，taker订单能够以合理价格成交
- 价差波动具有一定的持续性，不会在毫秒级别剧烈反转
- 用户账户在两个交易所都有足够的余额和保证金

### Dependencies
- Extended交易所WebSocket API和订单API正常工作
- Lighter交易所WebSocket API和订单API正常工作
- 现有的交易所客户端代码（exchanges/lighter.py和exchanges/extended.py）提供必要的价格获取和订单执行接口
- 现有的WebSocket管理代码（exchanges/lighter_custom_websocket.py）提供订单簿数据
