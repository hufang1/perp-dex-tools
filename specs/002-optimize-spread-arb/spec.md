# 功能规格说明: 优化价差套利策略

**功能分支**: `002-optimize-spread-arb`
**创建日期**: 2026-01-08
**状态**: 草稿
**输入**: 用户需求日志和问题描述

## 用户场景与测试

### 用户故事 1 - 避免单边持仓风险 (优先级: P1)

系统能够自动检测并处理单边持仓情况,避免长时间未对冲的敞口风险。

**优先级说明**: 这是核心风险控制需求。当前系统存在单边持仓超过2小时(8800秒)的情况,严重影响资金安全。

**独立测试**: 可以通过模拟订单部分成交场景来验证,当一笔订单只在一个交易所成交时,系统能够正确处理并决定是否平仓。

**验收场景**:

1. **鉴于** Extended交易所订单成交但Lighter订单失败, **当** 系统检测到单边持仓, **则** 自动平仓单边持仓并记录日志
2. **鉴于** 系统检测到单边持仓超过60秒, **当** 对冲订单仍未成交, **则** 执行紧急平仓操作
3. **鉴于** 单边持仓导致账户未对冲仓位数量超过阈值(0), **当** 系统检测到此情况, **则** 禁止开新仓直到单边仓位清除

---

### 用户故事 2 - 基于手续费的价差阈值优化 (优先级: P1)

系统根据实际手续费结构调整开仓阈值,提高交易频率同时保证盈利。

**优先级说明**: 直接影响策略盈利能力。Lighter免手续费而Extended taker费率0.0225%,阈值需要精确计算。

**独立测试**: 可以通过历史数据回测验证,价差超过0.0225%时开仓能否产生正收益。

**验收场景**:

1. **鉴于** Lighter和Extended价差超过0.0225%, **当** 系统检测到套利机会, **则** 执行开仓操作
2. **鉴于** 价差等于或低于0.0225%, **当** 系统计算潜在收益, **则** 放弃本次套利机会
3. **鉴于** 手续费政策发生变化, **当** 系统接收新配置, **则** 自动调整价差阈值

---

### 用户故事 3 - 智能平仓策略 (优先级: P1)

系统根据持仓时间和收益情况执行多层平仓策略,最大化资金利用效率。

**优先级说明**: 这是提高交易频率和收益率的核心逻辑。当前系统缺少动态平仓机制。

**独立测试**: 可以通过模拟不同市场行情(快速波动、横盘、趋势)验证平仓逻辑。

**验收场景**:

1. **鉴于** 开仓后价差盈利达到0.05%(覆盖2倍手续费), **当** 系统计算PnL, **则** 立即平仓锁定利润
2. **鉴于** 开仓后在配置的时间阈值(默认60秒)内未达盈利目标但PnL > 0, **当** 超过时间阈值, **则** 平仓获取小额利润
3. **鉴于** 开仓超过时间阈值后PnL仍 < 0, **当** 系统监控PnL, **则** 等待PnL转为0时立即平仓止损
4. **鉴于** 持仓超过最大允许时间(可配置,建议5分钟), **当** 无论PnL如何, **则** 强制平仓避免长期风险

---

### 用户故事 4 - 交易价格日志记录 (优先级: P2)

系统在开仓和平仓时记录详细价格信息,用于后续策略分析和优化。

**优先级说明**: 这是策略迭代的基础数据。当前日志缺少关键价格信息,无法验证策略执行效果。

**独立测试**: 可以通过执行一次完整套利流程,检查日志中是否包含所有必需的价格字段。

**验收场景**:

1. **鉴于** 系统执行开仓操作, **当** 订单成交, **则** 记录交易所、方向、价格、数量、时间戳
2. **鉴于** 系统执行平仓操作, **当** 订单成交, **则** 记录平仓价格、持仓时间、 realized PnL
3. **鉴于** 套利对完整结束, **当** 两笔平仓都完成, **则** 输出完整交易对总结(开仓价、平仓价、收益率)

---

### 边界情况

- 当WebSocket连接中断导致订单状态未知时,系统如何处理?
- 当市场价格在1分钟内剧烈波动导致PnL计算滞后时,系统如何响应?
- 当交易所API返回错误或超时时,系统如何保证数据一致性?
- 当同时存在多个套利机会但资金不足时,系统如何选择优先级?
- 当平仓订单部分成交时,系统如何处理剩余仓位?

## 需求

### 功能需求

- **FR-001**: 系统必须在检测到单边持仓超过60秒时自动执行紧急平仓
- **FR-002**: 系统必须在单边持仓存在期间禁止开新仓
- **FR-003**: 系统必须根据手续费结构动态计算价差阈值(当前为0.0225%)
- **FR-004**: 系统必须在价差超过阈值时才执行开仓操作
- **FR-005**: 系统必须在达到盈利目标时立即平仓
- **FR-006**: 系统必须在开仓1分钟后,若PnL > 0但未达盈利目标,则平仓获取小额利润
- **FR-007**: 系统必须在开仓1分钟后,若PnL < 0,则等待PnL转为0时平仓止损
- **FR-008**: 系统必须在每次开仓/平仓时记录完整的交易价格信息
- **FR-009**: 系统必须记录每笔交易的以下信息:交易所、交易对、方向、价格、数量、时间戳、订单ID
- **FR-010**: 系统必须在套利对完成时输出交易总结(包括开仓价、平仓价、持仓时间、总收益)
- **FR-011**: 系统必须在可配置的时间阈值(默认60秒)后执行基于时间的平仓决策,时间阈值可通过配置文件或环境变量调整,无需修改代码
- **FR-012**: 系统必须在价差盈利达到目标百分比(默认0.05%,即覆盖2倍以上手续费成本)时立即平仓锁定利润,盈利目标阈值可配置以适应不同风险偏好

### 关键实体

- **套利对(Spread Pair)**: 由Extended仓位和Lighter对冲仓位组成的交易对,包含开仓价格、平仓价格、持仓时间、PnL等属性
- **未对冲仓位(Unhedged Position)**: 仅在一个交易所成交的订单,需要特殊处理以控制风险
- **价差阈值(Spread Threshold)**: 基于手续费计算的最小盈利价差,当前为0.0225%
- **平仓策略(Closing Strategy)**: 包含时间阈值、PnL目标、强制平仓等多层决策逻辑

## 成功标准

### 可衡量的结果

- **SC-001**: 系统能够在100%的情况下避免单边持仓超过5分钟
- **SC-002**: 在单边持仓发生时,系统能够在60秒内完成自动平仓
- **SC-003**: 调整价差阈值后,套利机会识别准确率达到95%以上(基于历史数据回测)
- **SC-004**: 采用智能平仓策略后,平均持仓时间缩短至60秒以内
- **SC-005**: 系统记录的交易价格日志与交易所实际成交价格误差小于0.01%
- **SC-006**: 在测试环境中,系统能够处理至少10个并发套利对而不丢失日志数据
- **SC-007**: 策略优化后,单位时间内的套利交易次数提升30%以上
- **SC-008**: 采用多层平仓策略后,亏损交易比例降低至20%以下
- **SC-009**: 交易日志包含所有必需字段,且格式便于后续分析和回测
- **SC-010**: 系统在检测到风险时能够在10秒内停止开新仓操作

### 假设与约束

**假设**:
- Lighter交易所的taker和maker手续费保持为0
- Extended交易所的taker手续费为0.0225%,maker手续费为0
- 交易所API在正常情况下能够返回准确的订单状态
- WebSocket连接在大部分时间内保持稳定

**约束**:
- 必须优先考虑资金安全,避免长时间单边持仓
- 日志记录不能显著影响交易执行速度
- 平仓决策必须基于最新可用的市场数据
- 系统必须能够处理订单部分成交的情况
